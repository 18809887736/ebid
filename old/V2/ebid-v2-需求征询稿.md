# 电力招投标监控系统 v2 — 需求整理（外部征询稿）

> 用途：把 v2 实施方案浓缩成自包含的需求与决策清单，供外部 AI / 顾问评审。阅读本文无需访问代码仓库。
> 背景：v1 已在生产运行（Python 脚本 + Windows 任务计划），v2 是重写。方案已经过八轮外部评审迭代（前七轮做加法，第八轮做减法简化）。

## 1. 项目背景与硬约束

- **业务**：尽早、可靠地发现各电力集团的 AVC / AGC（自动电压控制 / 自动发电控制）招标公告，邮件通知本人，用于投标跟进。
- **维护者**：单人，非全职。**环境**：一台 Windows 11 家用电脑，本机 7×24 待机但不保证在线（整机不可用为已接受残余风险）。
- **现有 v1 覆盖 3 站**（v2 Phase 1 同范围）：
  1. 国能E招 chnenergybidding.com.cn —— urllib 直接抓取，无反爬；
  2. 华电 chdtp.com —— 瑞数反爬，需 ego(lite) 浏览器渲染；
  3. 大唐/犀维 cweme.cn —— 浏览器 page.fetch API。
  后续 Phase 2 按实测扩展到约 9 个公开站；Phase 3 才评估登录类站点。
- **浏览器**：ego(lite)（基于 Chromium 的 AI 浏览器，可被 Node.js 脚本驱动）。版本固定，升级先在开发空间验证。
- **邮件**：agently-cli（确定性命令行邮件工具）为主通道，SMTP 授权码为备用通道（DPAPI 加密存储）。

## 2. 目标与可靠性定义

- 核心目标：**不漏公告**（宁重勿漏），并尽早发现。
- 检查频率：每日 2 轮（08:30 / 14:30）+ 每日 09:40 一次 7 天宽窗兜底。最坏发现延迟 18h、平均 7.5h——已签认接受（原需求 ≤2h 已明确放松）。
- **可靠性定义**：任何单点故障（站点改版、抓取失败、任务没跑、邮件双通道故障）必须在 24 小时内以告警或日报异常可见。**「日报没到」本身就是人工介入信号**（日报每日固定发送，无新公告也发）。
- 关键词：AVC、AGC 及关联叫法（全称/简称/全半角），Phase 1 只匹配标题，宁可误报；每月人工抽检召回率。

## 3. 红线（不可违反的约束）

1. **生产链路无 LLM**：定时任务只走确定性脚本（任务计划 → run_check.py → ego-browser nodejs）；链路中无任何 AI Agent 命令行。AI 只在人在场时参与开发。上线前有 check_redline.py 自动扫描违规调用与非白名单域名。
2. **公告内容一律视为不可信数据**：只抽取白名单字段、限长、清洗控制字符；URL 强制白名单前缀；**绝不执行任何「报名/投标/提交」类操作**。
3. **邮件防投毒**：标题/机构名按文本节点 HTML 转义，URL 入 href 前校验 scheme；投毒场景有全链路测试覆盖。
4. 生产环境 URL 白名单不含 localhost；凭据 DPAPI 加密、仓库已转私有、git 历史已清理（曾泄露过，全部按已泄露处理）。

## 4. 功能需求

### 4.1 采集与去重
- 每站一个适配器文件（.mjs 浏览器站 / .py 静态站），故障隔离，单站失败不影响其他站。
- 适配器输出统一 JSON：site / run_id / ok / raw_count（过滤前总数）/ items[]（title、notice_type、published_date、url、native_id、deadline 等）/ 翻页元数据（exhausted、page_limit_hit、stop_reason、pages_fetched 必填）。
- **dedupe_key = 站点 + 公告类型 + (native_id 或 sha1(规范标题+日期))**，native_id 优先（免疫标题截断）；「变更公告」类型不同 = 新事件，正常送出。
- 数据库 SQLite 共 4 表：notices（公告）、runs（每轮）、site_runs（每站每轮）、site_state（连续失败数/告警时间）。
- 同键公告**只比 deadline** 字段变化（结构化字段中唯一必须通知的变更）；org/项目编号变化不重发——有意取舍，此类变化靠「变更公告」兜底。

### 4.2 通知（最关键需求）
- **发送成功才落库**（notified_at）；agently 两段式调用成功谓词 = 两段 returncode 均 0 且结构化解析 ok===true，任一不满足即视为未确认。
- 主通道失败 → SMTP 备用；**双失败 → 待发公告与告警落盘 data/alerts/pending.json + Windows 桌面通知，退出码 3，下一轮优先补发**（pending 与新发现按 dedupe_key 合并，每键一封）。
- 通知邮件包含结构化字段：标题、类型、发布时间、截止时间（deadline 尽量结构化为 ISO 格式）、链接。

### 4.3 可观测性与自愈
- **退出码契约**：0=正常；2=站点告警类；3=邮件双失败；4=等锁超时顺延。并存取最大优先级（3>4>2）。
- **告警规则**：单站连续失败 ≥2 轮告警（24h 节流）；恢复发通知；ego 整体无产出告警；告警也「成功才前移节流时间」。
- **改版判据分站**：列表站（国能、华电）此前有数据而 raw_count=0 → 疑似改版；时间窗站 = 7 天宽窗 raw_count 为 0 或响应结构校验失败才告警（窄窗安静日空结果是正常的，不告警）。
- 每轮追加写 runs.jsonl（容末尾半行）；state.json 一律临时文件+os.replace 原子写。
- **独立 watchdog 任务**（每小时、不依赖采集链路）：读 config/schedule.json 计算应触发时刻，3 小时仍无「成功运行」即告警。成功口径收窄为：trigger=main、生产模式、全站跑完、退出 0/2——手动跑/宽窗成功不算（活着≠主链路活着）。
- 每日日报（08:30 后）：各站成功/抓取/新增数、计划 vs 实际轮次、未决缺口、pending 未决告警。
- 漏跑自动补齐：时间窗起点 = max(now−7d, min(now−24h, 上次成功−1h))；超 7 天缺口不再自动追赶，日报列出，人工用 `--from --to` 手动补查。

### 4.4 并发与超时
- **run.lock 字节锁**（msvcrt.locking，进程死自动释放）：定时类等锁 20 分钟→仍失败记 deferred（退出 4）、下轮自动补做；manual 立即失败；watchdog 抢到锁=主链路活着，顺延。
- 主轮总超时 40 分钟 = 采集 ≤28（分站 4 分钟，超时跳站告警）+ 通知 ≥12（通知优先）；09:40 宽窗任务上限 80 分钟。
- 超时用 Popen + taskkill /T /F 清整棵进程树。

### 4.5 生产隔离
- 生产跑独立 git worktree（C:/work/ebid-prod，只检出阶段 tag）；runner 启动校验 worktree 干净且版本与 tag 相符，否则拒跑并告警。开发树不进任务计划。
- 数据备份：每日 VACUUM INTO 备份 SQLite（不直接拷文件），保留 14 份，integrity_check；runs 明细保留 400 天。
- 写库唯一入口都先取 run.lock（含 import/export 工具）。

## 5. 测试策略（已定案，是评审重点之一）

- **不做 mock 网站**（mockweb 已建成但封存不用）。两条腿：
  1. **真站标定回归**：利用「真站历史公告不改写」——时间窗圈定已知历史公告作为期望答案，回归时同参数请求真站断言抽取一致。每站 1–2 次请求，改适配器后与发布前必跑 + 月度人工抽检。
  2. **夹具单测**：无法向真站点播的场景（空列表/报错/超时/改版/截断/投毒）全部下沉为本地夹具 + 单测；投毒做全链路断言（夹具→适配器→清洗→邮件转义）。
- 单测无网络、无 Docker：假发送器门控、pending 合并、原子写故障注入、watchdog 口径、时间窗边界（BID_NOW 可注入，但生产读到测试开关即退出）。
- --replay 模式：读录制夹具 + 假发送器，演练通知自动化。
- E2E（pytest -m e2e）强制临时 data 目录、假发送器、dev-* 浏览器空间；SMTP 断言用进程内假接收器。

## 6. 阶段计划

| 阶段 | 内容 | 工作量 | 退出标准 |
|---|---|---|---|
| Phase 0 | 修 v1 三坑（邮件先落库/静默失败/无心跳）+ 任务计划 + 生产隔离 + doctor/runbook | 3–4 天 | 演练全过，无人值守 3 天 |
| Phase 1 | 适配器契约、SQLite、标定回归（原 3 站）、迁移与切换 | 4–6 天 + 并行观察 3 天 | 单测+标定全绿，并行 3 天一致后切换 |
| Phase 2 | 逐站实测接入（约 9 站）、正文二次匹配试点 1 站 | 每站 1.5–2 天 | 每站灰度 ≥3 天 |
| Phase 3 | 登录类站点（账密/验证码/Ukey 三模式） | 决策门通过才做 | — |

- **迁移切换三步**（runbook）：并行 3 天（V1 照常发信、V2 shadow 只记录不发）人工比对差异 → import_seen 导入 v1 已见清单（禁笼统 baseline）→ 人工核 V2 待发清单后置 notify:true，前两轮逐封核对。切换窗口少量重发已接受（宁重勿漏）。
- Phase 3 决策门三问：登录增量有多少？会话寿命实测多久？人工介入频率可接受吗？——不满足不做。

## 8. 请评审的问题

1. **可靠性定义**：「任何单点故障 24h 内可见 + 日报没到即介入」这套口径，对单人单机场景有没有漏掉的故障模式？（例：任务计划本身被禁用、电脑时间漂移、磁盘满。）
2. **最坏 18h 延迟**：对招投标公告的截标场景是否够用？（截标加查目前靠人工手动跑。）
3. **只比 deadline 的取舍**：org/项目编号变化不重发，靠变更公告兜底——实际站点不发变更公告时是否漏信息？
4. **砍掉 outbox 回到「发送成功才落库 + pending.json」**：崩溃窗口（邮件发出但未落库）会重发一封，是否可接受、有无更简单闭环？
5. **真站标定替代 mockweb**：依赖「历史公告不改写」，站点改搜索接口或删旧公告时标定即失效——月度抽检够不够兜住？
6. **时间窗 7 天自动补齐上限**：超过 7 天的缺口只人工补查，这个上限合理吗？
7. **整体**：以单人维护者的长期可维护性为最高优先级，这份方案还有没有过度设计或欠设计的部分？
